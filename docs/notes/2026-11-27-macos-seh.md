# Windows structured exceptions in the macOS loader

Follows `2026-11-27-macos-loader.md`. On Windows the kernel turns a fault into an exception and
ntdll dispatches it; on macOS `leonida-loader` now does both, for code in the images it mapped.

- `unwind.rs` (portable): the x64 `CONTEXT`, `.pdata` lookup and one-frame unwinding from
  `UNWIND_INFO`: every unwind code, chained entries, partial prologs, and frames stopped in an
  epilog, recognised by their instructions as Windows does.
- `seh.rs` (x86-64 macOS): `SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGFPE` and `SIGTRAP` in title code
  become `EXCEPTION_RECORD`s (access violation with read/write/execute and address, illegal
  instruction, divide by zero and overflow, breakpoint at the `int3` itself, single step). The
  handler builds them on the faulting thread's stack and returns into the dispatcher, which runs as
  ordinary code: vectored handlers first, then each frame's language handler. Faults outside title
  code go back to the handler installed before ours.
- Imports for title code, chained into the resolver with `seh_export`: `RtlCaptureContext`,
  `RtlRestoreContext`, `RtlUnwindEx`, `RtlUnwind`, `RaiseException`, `RtlRaiseException`,
  `RtlLookupFunctionEntry`, `RtlVirtualUnwind`, `AddVectoredExceptionHandler`,
  `RemoveVectoredExceptionHandler` (from ntdll, kernel32, kernelbase or their API sets). Those that
  need their caller's registers start with a stub that captures them into a `CONTEXT`.
- Our frames have no Windows unwind info. Where a walk reaches one (a handler called by the
  dispatcher), it goes on from the context of the exception being dispatched on that thread, which
  is where Windows' walk through ntdll's frames leads.

Not done, marked `shortcut:`: consolidated unwinds (`STATUS_UNWIND_CONSOLIDATE`, which C++
`catch` blocks under `__CxxFrameHandler4` use), and the nested and collided dispositions. Also not
done: `SetUnhandledExceptionFilter`, and the console-only instructions the Windows loader steps
over in a vectored handler (`console_insn.rs`).

One thing learnt from the test: a return address that falls on an epilog makes that frame read
as "in its epilog", so its handler is skipped. Windows does the same, which is why MSVC puts a
`nop` after a call that ends a function; the fixture does it too.

## Tested

Apple M5, macOS 26.6, Rosetta 2, Rust 1.98.1, 2026-11-27.

- `cargo test -p leonida-loader --target x86_64-apple-darwin --locked`: 14 passed, 3 ignored,
  five runs in a row. The stand-in title (`tests/fixtures/macos-probe`) has assembly functions
  with real `.seh_handler` unwind info. A fault in an inner frame is caught by the outer frame's
  handler, which unwinds to a landing with `RtlUnwindEx`; the inner frame's unwind handler runs, and
  the landing sees the outer frame's rbx again. The same with `RaiseException`. A vectored handler
  steps over a fault and the code goes on. An unhandled fault is reported as
  `unhandled exception 0xc0000005 at title+...` with the address, and ends the process.
- `cargo test -p leonida-loader --locked` on arm64: the 5 unwinding tests pass there too.
- Clippy with `-D warnings`: clean for `x86_64-apple-darwin`, `aarch64-apple-darwin`, and the
  workspace for `x86_64-pc-windows-msvc` (with and without `--all-features`, checked from the Mac
  with `CARGO_FEATURE_PURE=1`).

Not run on Windows, where nothing changes but an unused module.
