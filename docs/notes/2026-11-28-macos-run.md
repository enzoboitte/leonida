# macOS loader: DLL attach, TLS callbacks, title threads and the entry point

Follows `2026-11-27-macos-seh.md`. `crates/leonida-loader/src/macos.rs` now does what the Windows
loader and `threads.rs` do once an image is bound:

- **Static TLS of several images.** Each image with a TLS directory gets a slot of every thread's
  TLS array: an exe slot 0 (its code reads `gs:[0x58]` then `[0]` without reading `_tls_index`),
  DLLs the lowest free one from 1; `_tls_index` is written with it. A thread started before an
  image was mapped gets that image's block when it is mapped, as on Windows.
- **`MappedImage::attach`**: the image's TLS callbacks, then `DllMain(DLL_PROCESS_ATTACH)`; a
  `FALSE` from `DllMain` is an error.
- **`spawn_thread(start, param, stack)`**: a title thread, as `CreateThread` will start it: a TEB,
  then `DLL_THREAD_ATTACH` to every attached image in attach order (TLS callbacks, then `DllMain`),
  the thread procedure with the Windows x64 convention, then `DLL_THREAD_DETACH` in reverse order.
  `disable_thread_calls` (`DisableThreadLibraryCalls`) stops an image's `DllMain` thread notices;
  its TLS callbacks still hear of threads, as on Windows.
- **`MappedImage::run_main(dlls)`**: the title's main thread, with the stack size from the image
  header (at least 1 MiB): attaches the DLLs in order, runs the exe's TLS callbacks, then its entry
  point, and returns what the entry point returned.
- `enter_thread()` takes no image any more: it gives the thread the blocks of every mapped image.

The image list is not held while title code runs (a `DllMain` may map another image), and the
lock order is images, then threads' arrays.

Still to do for the loader on macOS: the console-only instructions (`console_insn.rs`, written
against Windows' `CONTEXT` and memory queries), `ExitThread`/`TerminateThread` (they need
`kernel32` on macOS first), `DLL_PROCESS_DETACH` at exit, and the `shortcut:`s of
`enter_thread` and `seh.rs`.

## Tested

Apple M5, macOS 26.6, Rosetta 2, Rust 1.98.1, 2026-11-28. The fixture `tests/fixtures/macos-probe`
now has a TLS callback and a `DllMain` that count their notices, a thread procedure, and a second
stand-in, `src/bin/probe_exe.rs`, an exe whose entry point returns 40 plus its own TLS variable.

`cargo test -p leonida-loader --target x86_64-apple-darwin --locked`: 16 passed, 3 ignored (the
`prepare` tests that read the test binary as a PE). Measured there: one `DLL_PROCESS_ATTACH` each
to the DLL's TLS callback and `DllMain`; a thread from `spawn_thread` returns its parameter plus
6 (a fresh copy of its TLS variable, 5) and is announced to both on start and end; after
`disable_thread_calls` only the TLS callback hears of the next thread; the exe, mapped after the
DLL, reads its block from slot 0 and returns 42 while the DLL still reads slot 1.

Clippy with `-D warnings` is clean for `x86_64-apple-darwin`, `aarch64-apple-darwin` and, from the
Mac with `CARGO_FEATURE_PURE=1`, `x86_64-pc-windows-msvc` (`--all-features`). Not run on Windows.
